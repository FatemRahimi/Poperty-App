## 3–5. Property Intelligence Kernel

The kernel owns **how** intelligence is identified, evidenced, assessed, versioned, snapshotted, and composed. It does **not** own domain methodology.

**Kernel owns**

- Canonical subject identity (listing / subject / future building-unit-parcel-title)
- Asset classification (including UNKNOWN)
- Evidence records and provenance
- Source type and time fields (`retrievedAt` ≠ `evidenceAsOf` ≠ `observedAt` ≠ `analysisAt`)
- Assessment-state mapping (adapter, not a rewrite)
- Domain result envelope and domain availability
- Unresolved dependencies and investigation priorities as structures
- Decision contribution contract
- Immutable snapshot semantics
- Version metadata
- Privacy visibility (SHARED vs PRIVATE)
- Provider-cost classification on domain registration
- Failure isolation for composition

**Kernel does not own**

- Commercial / agricultural / industrial / land valuation formulas
- Legal conclusions
- Planning permission conclusions
- Construction-cost formulas
- Project scheduling
- Portfolio optimisation formulas
- LLM-generated facts

Live engines remain plugins. The current residential PI report stays the production path until a domain is explicitly implemented and wired.

## 6–7. Asset class and subtype

Canonical classes: `RESIDENTIAL`, `COMMERCIAL`, `INDUSTRIAL`, `AGRICULTURAL`, `LAND`, `DEVELOPMENT_SITE`, `MIXED_USE`, `UNKNOWN`.

- `UNKNOWN` is valid and default.
- Listing `property_type` / `category` does **not** imply a class.
- Inference is allowed only with explicit source + confidence, labelled `INFERRED`.
- Subtypes are an extensible ID list per class (`flat`, `office`, …). Unregistered subtypes are stored as custom IDs (`registered: false`) and do not invent a class.

---

## 8. Identity model

Entities are not interchangeable:

| Kind | Meaning |
|---|---|
| LISTING | Marketplace record (`properties.id`) |
| SUBJECT | Analysis subject (`intelligence_subjects.id`, often UPRN-keyed) |
| PROPERTY | Legal/economic asset as analysed |
| BUILDING | Structure that may contain units |
| UNIT | Occupiable part of a building |
| LAND_PARCEL | Cadastral/land unit |
| TITLE | Legal title (a transaction may involve many) |
| SITE / DEVELOPMENT_SITE | Combined land interest (asset/site identity, not a project) |
| DEVELOPMENT_PROJECT | Proposed body of work (foundation only; not live) |
| DEVELOPMENT_SCENARIO | One configuration under a project (not Finance What-if) |

Relations (`CONTAINS`, `WITHIN`, `PART_OF`, `ADJACENT`, `UNKNOWN`) never claim legal or cadastral match. This phase does not implement matching.

Current production identity remains listingId + subjectId + optional UPRN/address/postcode/coordinates.

## 9–11. Evidence, taxonomy, provenance

Mandatory: `domain`, `subjectRef`, `factType`, `classification`, `sourceType`, `provenance.source`.

Optional: value, unit, timestamps, spatial relation, trust, limitations, visibility, sourceRecordId.

**Classification:** `FACT`, `AREA_CONTEXT`, `DERIVED`, `USER_INPUT`, `SCENARIO`, `INFERENCE`, `NOT_ASSESSED`.

Examples: listed-building match → FACT if authoritative; nearby school → AREA_CONTEXT; gross yield → DERIVED; user budget → USER_INPUT/SCENARIO; development potential → INFERENCE, never silent FACT.

**Source types:** `OFFICIAL`, `LICENSED_PROVIDER`, `FIRST_PARTY`, `USER_REPORTED`, `DERIVED`, `MODEL_ASSISTED`.

`MODEL_ASSISTED` is never authoritative, even if a caller sets `authoritative: true`.

Missing value stays `null`. Missing ≠ false. Missing ≠ 0. Empty ≠ none.

---

## 12. Assessment-state model

Kernel states: `ASSESSED`, `NOT_ASSESSED`, `INSUFFICIENT_EVIDENCE`, `NOT_APPLICABLE`, `INVALID_INPUT`, `UNAVAILABLE`.

Existing names (`assessed`, `notAssessed`, `available`, valuation `assessmentState`, finance `metricAssessment.state`) are **mapped** by `mapExistingAssessment`. Live contracts are not renamed.

---

## 13–15. Domain envelope, registry, dependencies

Envelope: `{ domain, version, subject, status, evidenceAsOf, assessment, findings, evidence, limitations, unresolvedDependencies, investigationPriorities, provenance }`.

Status: `AVAILABLE` | `PARTIAL` | `NOT_ASSESSED` | `UNAVAILABLE`.

Registered domains (stable IDs): IDENTITY, MARKET, VALUATION, RENTAL, FINANCE, LEGAL_TITLE, PLANNING, ENVIRONMENT, BUILDING_CONDITION, MAINTENANCE_CAPEX, DEVELOPMENT, PROJECT_COST, DEVELOPMENT_FEASIBILITY, PROJECT_MANAGEMENT, ASSET_MANAGEMENT, PORTFOLIO, DECISION.

Dependency direction (no cycles):

```
IDENTITY
  ├── MARKET → VALUATION
  ├── MARKET → RENTAL
  ├── FINANCE
  ├── PLANNING → DEVELOPMENT
  ├── ENVIRONMENT
  ├── LEGAL_TITLE
  └── BUILDING_CONDITION → MAINTENANCE_CAPEX
                       → PROJECT_COST → DEVELOPMENT_FEASIBILITY
                                       → PROJECT_MANAGEMENT
ASSET_MANAGEMENT ← FINANCE, RENTAL
PORTFOLIO ← VALUATION, RENTAL, FINANCE
DECISION consumes assessed outputs; it does not block other domains
```

Future engines are `wiredIntoLiveAnalysis: false`.

## 16. Asset-class capability matrix

`SUPPORTED` | `CONDITIONAL` | `NOT_APPLICABLE` | `FUTURE` | `UNKNOWN`

Current residential valuation is **SUPPORTED** only for `RESIDENTIAL`. Commercial, industrial, agricultural, land, and development valuation are **FUTURE** — not the existing residential engine.

Rental is SUPPORTED for residential; NOT_APPLICABLE for bare land / development site as a default let; CONDITIONAL or FUTURE elsewhere.

Building condition is NOT_APPLICABLE for LAND.

Finance math is CONDITIONAL on other classes (inputs exist; current BTL presentation is residential).

## 17–19. Units, time, space

Units stay on the value. `GBP_PER_SQFT` ≠ `GBP_PER_SQM`. No silent conversion.

Time fields are distinct: `retrievedAt`, `evidenceAsOf`, `observedAt`, `effectiveFrom`, `effectiveTo`, `analysisAt`, `documentDate`, `inspectionDate`.

Spatial relations: `SUBJECT`, `SAME_SITE`, `CONTAINS`, `WITHIN`, `INTERSECTS`, `NEARBY`, `AREA_CONTEXT`, `UNKNOWN`. Proximity is not title, ownership, or planning status.

---

## 20. Legal safety boundary

LEGAL_TITLE foundation (`legal-title-domain-0.1.0`) may represent evidence completeness, adjacent tenure/lease facts, missing documents, and conflicts.

It is **not** wired into live analysis. Title register and title plan are **not available**.

It must not act as a solicitor, declare title good/bad, invent covenants/easements, or treat missing data as “no restriction”.

BUILDING_CONDITION foundation (`building-condition-domain-0.1.0`) may represent inspection completeness and adjacent energy/layout artefacts.

It is **not** wired into live analysis. An EPC, floor plan, photograph, or `buildRisks` heuristic is **not** a condition survey.

DEVELOPMENT foundation (`development-domain-0.1.0`) may represent project identity, scenario, work scope, and known/unresolved dependencies when a project is supplied.

It is **not** wired into live analysis. Finance What-if is **not** a development project. A project does **not** imply permission, ownership, cost, schedule, or feasibility.

---

## 21. Project / cost safety boundary

`DEVELOPMENT_PROJECT` is identity and scope only (`development-project-contract-0.1.0`).

PROJECT_COST foundation (`project-cost-domain-0.1.0`) may represent quotes, actuals, user budgets, benchmarks, and deterministic subtotals when cost items are supplied.

It is **not** wired into live analysis. A user budget is **not** assessed project cost. A quote is **not** an actual. `renovationCost` remains a frozen finance input.

Project Management kinds (future): planned, actual, forecast, dependency, approval, risk, variation.

No estimating, inflation, GDV, or residual in this phase.

---

## 22. Multi-asset valuation boundary

```
CURRENT RESIDENTIAL VALUATION
  ≠ FUTURE COMMERCIAL VALUATION
  ≠ FUTURE INDUSTRIAL VALUATION
  ≠ FUTURE AGRICULTURAL VALUATION
  ≠ FUTURE LAND / DEVELOPMENT VALUATION
```

Do not reuse residential comparables, £/sqft blends, or AVM inputs merely because they exist.

---

## 23–24. DI V2 and LLM

A domain may emit `materialFindings`, `unresolvedDependencies`, `investigationPriorities`, `sensitivityDrivers`, `limitations`. DI consumes them. `createsDomainFacts: false`.

Deterministic systems produce facts and calculations. LLM may explain, summarise, navigate, or extract only when validated. LLM is never valuation, legal, planning, cost, or scheduler authority.

---

## 25. Snapshot / history

`AiRequest.create` remains insert-only. New domains must persist `domain`, `version`, `evidenceAsOf`, `analysisAt`, and provenance on the snapshot. Historical rows are never rewritten. V1.1 / v2 reports remain readable without new required fields.

---

## 26–27. Privacy and provider cost

Private: finance assumptions, mortgage, budgets, quotes, uploaded legal documents, portfolio ownership, scenarios, notes, proposed development, project scope, development scenarios, project budgets, contractor/supplier quotes, invoices, cost assumptions.

Shared identity never implies shared private analysis.

Domain registration declares `dataAccess` (`DB_ONLY`, `OPEN_DATA`, `LICENSED_PROVIDER`, `USER_DOCUMENT`, `DERIVED`, `MODEL_ASSISTED`) and `mayIncurProviderCost`. No new providers or quota changes in this phase.

---

## 28–29. Failure isolation and report composition

One domain `UNAVAILABLE` or `NOT_ASSESSED` must not erase others. Failure is not empty evidence.

Future report order (not implemented): Identity → Current decision → Key findings → Unknowns → Market/valuation → Income/finance → Legal → Planning/development → Building → Project/cost → Environment → Asset management → What-if.

Do not rebuild `IntelligenceReport` now.

---

## 30–31. Versioning and migration

New kernel versions are additive. Frozen production version strings are never reused.

Migration: adapters, optional fields, parallel domain outputs. No big-bang rewrite, no snapshot rewrite, no forcing old reports into new schemas.
